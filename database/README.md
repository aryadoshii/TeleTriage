# database/

This directory holds TeleTriage's knowledge base, cache, and the raw/
intermediate artifacts of the data pipeline that builds them. Most of it
is **gitignored** — regenerated by scripts, not source-controlled — so
this file exists to explain what's missing after a fresh clone, and how
to get it back.

## Generated vs committed

| File | Status | What it is |
|---|---|---|
| `real_kb.jsonl` | Generated (gitignored) | Raw 3GPP spec chunks scraped by `scrape_data.py` |
| `real_cache_candidates.jsonl` | Generated (gitignored) | Synthetic Q&A candidates from `synth_qa.py`, before quality gating |
| `synth_kb.jsonl` | Generated (gitignored) | Candidates that passed both quality gates — the active retrieval corpus |
| `raw_zips/` | Generated (gitignored) | Cached 3GPP spec ZIP downloads |
| `indexes/` | Generated (gitignored) | Built BM25 + FAISS indexes + manifest (`build_index.py` output) |
| `sample_kb.jsonl` | **Committed** | 30 hand-curated seed KB entries, used in tests |
| `sample_cache.json` | **Committed** | Hand-curated cache entries (Tier 1 / CAG) |
| `synth_kb_sample.jsonl` | **Committed** | Stratified sample of `synth_kb.jsonl` — see below |

**Why `synth_kb_sample.jsonl` exists:** `real_kb.jsonl` and `synth_kb.jsonl`
are gitignored (`real_kb.jsonl` alone is ~9 MB), so a fresh clone of this
repo has no way to see or reproduce the corpus the evaluation numbers in
the main README are based on. `synth_kb_sample.jsonl` is a small,
proportionally-stratified-by-spec sample that *is* committed, so the
shape of the corpus is inspectable without regenerating anything.

`database/synth_probe.jsonl` and `database/synth_probe2.jsonl` are ad-hoc
outputs from earlier development probes (prompt/scoring iteration), not
part of the regular pipeline — currently untracked, safe to delete.

## Regenerating from scratch

Run in order:

```bash
# 1. Scrape + chunk 5 3GPP specs, apply density/front-matter/references/
#    boilerplate filters, MinHash-dedup -> database/real_kb.jsonl
uv run python scripts/scrape_data.py

# 2. Generate synthetic Q&A pairs over those chunks via Groq/Gemini,
#    scoring each pair's grounding_score and utility_score ->
#    database/real_cache_candidates.jsonl
#    (resumable across days/quota limits — see --resume, --token-budget)
uv run python scripts/synth_qa.py

# 3. Filter candidates through both quality gates and reshape into the
#    KB schema build_index.py expects -> database/synth_kb.jsonl
uv run python scripts/build_synth_kb.py

# 4. Build BM25 + FAISS indexes from the KB
uv run python scripts/build_index.py --kb database/synth_kb.jsonl

# 5. (Optional) Refresh the committed sample after the KB changes size/shape
uv run python scripts/make_kb_sample.py
```

## This is a work in progress

264 candidates is not the final corpus size — `synth_qa.py` has only been
run against a fraction of the 7,236 chunks in `real_kb.jsonl` so far.
Continue it with:

```bash
uv run python scripts/synth_qa.py --resume --max-chunks <bigger-number>
```

`--resume` skips chunks already present in `real_cache_candidates.jsonl`
(matched by `source_chunk_id`), so this is safe to run repeatedly across
multiple days/quota resets without reprocessing anything. This file does
**not** need editing every time more candidates are added — only the
"Observed counts" table above needs an occasional refresh, and only the
final total really matters (re-run `build_synth_kb.py` and
`make_kb_sample.py` after a significant batch, update the counts table).
